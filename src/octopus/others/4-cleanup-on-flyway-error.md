Documentation: `cleanup_on_flyway_error.ps1`
============================================

📜 Overview
-----------

This PowerShell script provides an automated cleanup mechanism for failed [Flyway](https://flywaydb.org/) database migrations. When a database deployment fails, Flyway's schema history table may be left in a locked state or contain a record of the failed migration, preventing future attempts. This script reverts those changes, enabling the deployment to be re-run.

Its primary functions are:

1.  **Database Cleanup**: Removes the entry for the failed migration from Flyway's schema history table.

2.  **Filesystem Cleanup**: Deletes the SQL script files that were downloaded to the deployment agent for the failed version.

This script is designed to be executed within a CI/CD pipeline, specifically as a **failure step** in a tool like **Octopus Deploy**.

* * * * *

⚙️ How It Works
---------------

The script follows a logical flow to safely determine if a cleanup is necessary and then execute it.

### Execution Flow

1.  **Initialization**: The script sets its working directory and imports helper functions from other PowerShell modules (`FlywayFunctionsGenericDBOctopus.ps1`, etc.).

2.  **Authentication**: It securely retrieves temporary AWS credentials that were generated by a preceding "Assume Role" step in the Octopus Deploy process.

3.  **Configuration Loading**: It reads a central XML configuration file (`.xml`) based on the target database. It then parses this file to find the settings for the specific environment being deployed to (e.g., `dev`, `staging`).

4.  **Database Credentials**: Using the AWS credentials, it connects to **AWS Secrets Manager** to fetch the database username and password. This avoids storing sensitive information in source control.

5.  **Identify Failed Version**:

    -   It queries the database's Flyway schema history table (e.g., `flyway_schema_history`) to find the most recent migration version that was attempted.

    -   It compares this version with the version number of the release that was being deployed (passed in as a variable, `$RELEASE`).

6.  **Conditional Cleanup**:

    -   **If the versions match**, it confirms that the failed deployment did indeed start and create a record. The script then proceeds to:

        -   Call a `CleanDatabase` function to execute a `DELETE` statement against the history table for that specific version.

        -   Call a `CleanFiles` function to remove the corresponding `V<version>__*.sql` or `R<version>__*.sql` files from the local disk.

    -   **If the versions do not match**, it assumes the deployment failed before Flyway made any database changes. In this case, no cleanup is needed, and the script simply logs a message and exits successfully.

7.  **Error Handling**: The entire cleanup logic is wrapped in a `try/catch` block to handle any unexpected errors during the process, ensuring the CI/CD pipeline is properly notified of a failure.

🔧 Dependencies and Configuration
---------------------------------

For the script to function correctly, the following must be in place:

### Tools

-   **PowerShell**: The script execution engine.

-   **AWS CLI**: Required to fetch secrets from AWS Secrets Manager.

-   **Octopus Deploy** (or a similar CI/CD tool): The orchestrator that triggers the script and provides the necessary variables.

### Input Variables

The script relies on several variables being passed from the deployment tool:

-   `$DATABASE`: The name of the database (e.g., `MyApplicationDB`), used to locate the correct config file.

-   `$SELECT_ENVIRONMENT`: The target environment (e.g., `dev`, `staging`, `prod`).

-   `$RELEASE`: The release or version number being deployed (e.g., `1.15.2`).

-   `$REDEPLOY`: A boolean (`'True'` or `'False'`) indicating if the migration is a repeatable migration.

-   `$OctopusParameters[...]`: Octopus-specific variables containing the temporary AWS credentials.

### Configuration File

A central `.xml` file is used to store environment-specific details, such as:

-   Database connection details (URL, port, ODBC driver).

-   The AWS Secret ID for database credentials.

-   File paths for storing SQL scripts.

-   The name of the Flyway schema history table.

### Helper Scripts

The actual logic for database and file operations is abstracted into functions within these sourced files:

-   `DeployDatabaseVersionsGenericDBOctopus.ps1`

-   `FlywayFunctionsGenericDBOctopus.ps1` (contains `CleanDatabase`, `LatestVersionDeployed`)

-   `GitFunctionsGenericDBOctopus.ps1`

🚀 Usage
--------

This script is **not intended to be run manually**. It should be configured as an automated step in an Octopus Deploy process that runs **only on failure of the main database deployment step**.

This ensures that the environment is automatically cleaned and prepared for a subsequent deployment attempt without manual intervention, making the CI/CD process more robust and resilient. ✨
